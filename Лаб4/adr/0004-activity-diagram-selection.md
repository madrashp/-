# ADR 0004: Вибір нотації Activity Diagram та узгодження атрибутів Loan

- **Статус:** Accepted
- **Дата:** 2026-11-23

## Контекст та постановка проблеми
Для моделювання життєвого циклу видачі книги потрібно обрати одну формальну нотацію (Activity, BPMN або State Machine) та узгодити кроки процесу з ER-моделлю Завдання 1, де у сутності `Loan` відсутнє поле `status`, а у `Book` немає `is_available`.

## Розглянуті варіанти
1. **State Machine (`stateDiagram-v2`):** Описує переходи станів однієї сутності, але не відображає розподіл дій між користувачем, бібліотекарем та зовнішнім сервісом сповіщень.
2. **BPMN 2.0 XML:** Потужний стандарт, але генерує надлишковий XML-код, складний для текстового рев'ю в Git.
3. **PlantUML Activity Diagram зі Swimlanes:** Дозволяє розділити відповідальність між акторами, показати паралельні дії (`fork/join`) та сигнали повідомлень, оперуючи лише наявними атрибутами ER-моделі (`borrowed_at`, `due_date`, `returned_at`).

## Результат рішення
Обрано варіант **3 (PlantUML Activity Diagram зі Swimlanes)**. Замість вигаданих полів `status` та `is_available` перевірка наявності книги та стан видачі визначаються за заповненістю дат `borrowed_at` і `returned_at` у таблиці `Loan`.

## Наслідки
- **Добре:** Повна узгодженість із ER-моделлю Завдання 1 без потреби змінювати схему даних.
- **Добре:** Наочне розділення дій користувача, бібліотекаря та автоматизованої системи.
- **Погано:** Складні розгалуження (перевірка боргів + скасування + прострочення) збільшують висоту діаграми.
