# Специфікація бізнес-процесу — Завдання 4

## 1. Обраний процес і зв'язок із попередніми завданнями
Моделюється повний бізнес-процес бронювання, видачі та повернення книги (`Loan Lifecycle`).
Процес охоплює прецеденти із Завдання 2:
- **UC-05**: Створення запиту на бронювання книги.
- **UC-06**: Скасування бронювання користувачем до моменту видачі.
- **UC-09**: Фіксація видачі та підтвердження повернення книги бібліотекарем.
- **UC-10**: Формування нагадувань про прострочений термін повернення.

## 2. Обрана нотація та обґрунтування
Для опису обрано **PlantUML Activity Diagram** із розділенням на доріжки ролей (swimlanes): `User`, `E-Library System`, `Librarian`, `Notification Service <<System>>`.
- Вибір Activity-діаграми замість машини станів (`stateDiagram-v2`) зумовлений потребою показати взаємодію між чотирма різними учасниками, а не лише зміну станів одного об'єкта.
- Вибір PlantUML замість BPMN 2.0 XML дозволяє зберігати модель у компактному текстовому форматі, зручному для контролю версій у Git.

## 3. Узгодженість із ER-моделлю (Завдання 1)
У ER-моделі Завдання 1 сутність `Book` не має атрибута `is_available`, а сутність `Loan` не має атрибута `status` (наявні лише `borrowed_at`, `due_date`, `returned_at`).
Рішення:
1. Доступність книги визначається відсутністю активного запису `Loan` для цієї книги (де `returned_at` порожнє).
2. Запис `Loan` створюється під час бронювання, поле `borrowed_at` та `due_date` фіксуються у момент фізичної видачі книги бібліотекарем, а `returned_at` — у момент її повернення.

## 4. Аудит повідомлень між учасниками

| Повідомлення | Відправник | Отримувач | Поведінка процесу за відсутності відповіді |
|---|---|---|---|
| Повідомлення про блокування через борги | `E-Library System` | `User` | Процес завершується одразу після відправки (fire-and-forget); відповідь користувача не потрібна. |
| Повідомлення про відсутність книги | `E-Library System` | `User` | Процес завершується одразу після відправки; система не очікує реакції. |
| Підтвердження бронювання | `E-Library System` | `User` | Система очікує або візит користувача для отримання книги, або запит на скасування бронювання (UC-06). Якщо користувач не приходить — бронювання залишається активним до скасування. |
| Тригер про прострочення (UC-10) | `E-Library System` | `Notification Service <<System>>` | Асинхронний виклик; основний процес не зупиняється, навіть якщо сервіс сповіщень тимчасово недоступний. |
| Лист-нагадування про борг | `Notification Service <<System>>` | `User` | Неблокуюче повідомлення. Якщо читач ігнорує лист, запис `Loan` лишається неповерненим (блокує нові замовлення за ADR 0002) до фізичного візиту в бібліотеку. |
| Підтвердження закриття видачі | `E-Library System` | `User` | Фінальне сповіщення; процес завершується без очікування відповіді. |

## 5. Звірка зі сценаріями Gherkin (Завдання 2)

| Сценарій Gherkin (Завдання 2) | Шлях на Activity-діаграмі (Завдання 4) |
|---|---|
| `US-02 / Відмова у бронюванні через наявність боргів` | Перевірка боргів → гілка «так» → «Повідомити про блокування через борги» → завершення процесу. |
| `US-02 / Успішне бронювання книги` | Перевірка боргів («ні») → перевірка наявності («так») → створення запису `Loan` → паралельне оновлення каталогу та підтвердження → видача книги бібліотекарем (`borrowed_at`, `due_date`). |
| `UC-06 / Скасування бронювання` | Після підтвердження бронювання → гілка вибору користувача «Скасувати бронювання?» («так») → видалення запису `Loan` → повідомлення про скасування → завершення. |
| `US-03 / Успішне повернення книги` | Візит до бібліотеки → прийом книги бібліотекарем → фіксація `returned_at` → повідомлення про закриття видачі → завершення. |
